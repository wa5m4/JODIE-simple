## 3. 真正的根因：分区规模偏差（Partition Scale Bias）

### 3.1 为什么 seed 修复无效

seed 修复去掉了 `+ partition_id`，使所有分区使用相同的初始 RNG 状态。但这只是消除了随机噪声（~0.002 级别的 MRR 波动），无法解决架构排名本身被 Pipeline 训练范式系统性地改变的问题。

随机噪声的消除不会改变"402K > 133K"这个 Pipeline 下的基本排序关系，因为这个排序关系不是随机噪声造成的。

### 3.2 真正的问题：训练-评估范式不匹配

```
┌─────────────────────────────────────────────────────────────────┐
│                   Pipeline NAS 的架构排名偏差                       │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  Pipeline 评估的问题:                                              │
│    "在 500 个交互的分区上训练 2 epoch，哪个架构验证分数最高？"           │
│                                                                 │
│  Serial 最终评估的问题:                                             │
│    "在 14,000 个交互上训练 5 epoch，哪个架构测试分数最高？"             │
│                                                                 │
│  这是两个不同的问题 — 有不同的答案。                                  │
│                                                                 │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  小数据 (500 interactions/partition) → 大模型占优                   │
│    - 402K 参数的模型能快速拟合 500 个交互中的模式                       │
│    - static_embeddings 提供直接的 user/item 记忆能力                  │
│    - time_proj=linear 提供额外的时序建模能力                          │
│    - 小数据上的过拟合在 partition-level eval 中不被惩罚                 │
│                                                                 │
│  大数据 (14,000 interactions) → 小模型占优                           │
│    - 133K 参数的模型泛化更好，不容易过拟合到噪声                         │
│    - 不需要 static_embeddings — RNN 动态嵌入已经足够                    │
│    - 不需要 time_proj — 简单的 delta_time 足够                       │
│    - 全数据训练下，简洁架构的泛化优势充分体现                            │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 3.3 为什么 Data Parallel 没有这个问题

Data Parallel 虽然也使用分区，但每个 worker 看到的是**完整数据的随机子集**（而非连续的时间分区），且 worker 间同步梯度。这保证了：

1. 每个 worker 的训练数据分布与全数据集一致（只是样本量不同）
2. 梯度同步使模型更新方向与 Serial 一致
3. val_score 基于全数据评估（而非分区评估）

因此 Data Parallel 的 val_score 排名与 Serial 一致，选出了相同的架构。

### 3.4 JODIE 模型的特殊性

JODIE 是一个 RNN-based 模型，其核心是用户/物品嵌入随时间的动态更新。在 Pipeline 的分区训练中：

- **RNN 状态在每个分区边界被 detach 并传输**。这意味着梯度不会跨分区回传，每个分区是一个独立的训练单元。
- **static_embeddings=on** 为每个用户/物品学习一个不随时间变化的静态嵌入，可以绕过 RNN 状态转移带来的信息损失。在小分区场景下，这是巨大的优势。
- **time_proj=linear** 添加了一个额外的线性变换来处理时间间隔，增强了模型对局部时序模式的拟合能力。

这些特性在小分区训练中是优势，但在全数据训练中变成了冗余——RNN 本身有足够的容量从完整序列中学习。

## 5. 方案 C 实验结果（2026-08-09 新增）

### 5.1 方案 C 设计

```
训练: Pipeline 分区训练 (run_train_only, 快)
  → 返回 trained payloads (model_state_dict + runtime_state)
评估: 全数据验证集 (evaluate_ranking_metrics on full val_data, 准)

```

**关键假设**: 如果问题只是"分区评估低估了小模型"，那全数据评估应该纠正排名。

### 5.5 关键分析：为什么方案 C 失败了

方案 C 的失败揭示了一个比"评估偏差"更根本的问题：**训练偏差（Training Bias）**。

```
┌─────────────────────────────────────────────────────────────────┐
│          评估偏差 vs 训练偏差                                    │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  评估偏差 (Plan C 修复):                                         │
│    Pipeline 分区评估 → 402K 在小分区上得分虚高                     │
│    全数据评估        → 消除此偏差 ✓                               │
│                                                                 │
│  训练偏差 (Plan C 无法修复):                                      │
│    Pipeline 分区训练 → 402K 模型真的被训练得更好                   │
│    Serial 全数据训练 → 133K 模型真的被训练得更好                   │
│                                                                 │
│  即使评估方式完全相同（全数据），经 Pipeline 训练的模型和             │
│  经 Serial 训练的模型具有不同的最优架构。                          │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

**用数据说话**:
- 402K 模型经 **pipeline 训练** 后全数据 val_score = **0.7802**
- 133K 模型经 **pipeline 训练** 后全数据 val_score = **0.7481**
- 402K > 133K（pipeline 训练下），差距 Δ = 0.032

- 402K 模型经 **serial 训练** 后全数据 val_score = **0.7855**
- 133K 模型经 **serial 训练** 后全数据 val_score = **0.8648**
- 133K > 402K（serial 训练下），差距 Δ = 0.079

**结论**: Pipeline 训练本身就改变了不同架构的相对优势。这不是评估偏差，而是在不同训练范式下，同一个架构会收敛到不同质量的模型。这是**系统性偏差，无法通过改进评估来消除**。

### 5.6 为什么 test_plan_c.py 看起来有效

单阶段验证测试中，133K (0.7747) > 402K (0.6747)，排名正确。但在 3 阶段全量运行中，402K 反超。

原因：多阶段 pipeline 训练（3 阶段 × 28 分区）让大模型有更多机会利用每阶段的"新数据"，积累优势。单阶段训练只有 ~4500 个交互，不足以体现大模型的过拟合优势。

## 6. 修复方案

### 方案 A：增加分区大小（最简单）

### 方案 B：两阶段搜索（Pipeline 粗筛 + Serial 精筛）

```
Phase 1: Pipeline 快速粗筛（~100 trials × 1 epoch）→ 选出 top 20
Phase 2: Serial 精确评估 top 20 × 2 epochs → 选出 top 8
Phase 3: Serial rerank top 8 × 5 epochs → 最终架构
```

### ~~方案 C：全数据评估~~ ❌ 已测试，无效

方案 C 已于 2026-08-09 完整实现并验证。Pipeline 分区训练 + 全数据评估的结果与旧运行完全相同。根因是训练偏差（pipeline 训练本身就改变了模型质量排序），不是评估偏差。详见第 5 节。

### 方案 D：使用固定架构搜索空间

限制搜索空间为更小的、已知在 serial 下表现良好的架构子集，避免 RL controller 被 Pipeline 评分误导到极端架构。

## 8. 建议的下一步

1. **立即**：方案 A — 将 `partition_size` 从 500 增加到 2000-5000，观察训练偏差是否减小
2. **短期**：方案 B — 两阶段搜索（Pipeline 粗筛 + Serial 精筛），利用 Pipeline 速度同时保证架构质量
3. **中期**：直接使用 Data Parallel 替代 Pipeline 作为 NAS 加速策略。DP 已经达到 Serial 的 2x+ 速度，且**完全没有排名偏差**（选出与 Serial 完全相同的架构，test_score=0.8561）
4. **长期**：如需继续使用 Pipeline，需重新设计训练范式（梯度跨分区回传、overlap 分区、增加 partition_size 至接近全数据），从根本上消除训练偏差
